## Context

DataSpec contracts currently support three constraint types: `unique` (boolean), `not_null` (boolean), and `ref` (string). The constraint system is well-established with consistent patterns across the TypeScript interface, YAML parser, and JSON schema. Issue #12 requests adding an `allowed_values` constraint to restrict string fields to a defined set of permitted values, similar to enum functionality.

## Goals / Non-Goals

**Goals:**

- Add `allowed_values` constraint that accepts an array of strings
- Restrict the constraint to `type: string` fields only
- Maintain consistency with existing constraint patterns (parsing, validation, schema)
- Provide clear error messages when constraint is misused (e.g., on non-string fields)

**Non-Goals:**

- Supporting numeric or boolean allowed values (string-only for v1)
- Auto-generating TypeScript enums or other code generation
- Runtime validation of data against constraints (parsing only for now)

## Decisions

### Decision: Array of strings vs object format

**Choice**: `allowed_values: ['a', 'b', 'c']` (simple array)

**Rationale**: Matches the simplicity of existing constraints. An object format (e.g., `{ values: [...], message: '...' }`) adds complexity without clear benefit at this stage. Error messages can be generated by the parser/validation layer.

**Alternatives considered**:

- Object with `values` and optional `message` - rejected as over-engineering for v1
- Comma-separated string - rejected as less idiomatic in YAML

### Decision: Parser validation for string-only constraint

**Choice**: Parser validates that `allowed_values` is only used with `type: string`

**Rationale**: Fail fast at parse time rather than allowing invalid configurations. Consistent with how other constraints are validated (e.g., `ref` must be a string).

**Alternatives considered**:

- Allow on any type and validate at runtime - rejected as it defers errors
- Schema-level restriction only - rejected as insufficient (schema can't check cross-field constraints)

## Risks / Trade-offs

- **Risk**: Future need for non-string allowed values → **Mitigation**: Can extend to support `(string | number)[]` later without breaking changes
- **Risk**: Empty array is valid but useless → **Mitigation**: Parser could warn, but not block (empty means "no values allowed" which is technically valid)
